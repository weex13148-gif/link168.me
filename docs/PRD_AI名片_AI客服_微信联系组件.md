# Link168 AI名片、AI客服与微信联系组件 PRD

**版本：** v1.0  
**日期：** 2026-07-12  
**状态：** 已确认，作为下一轮开发输入  
**适用分支：** `codex/link168-v2-direction`  
**上位规则：** `PRODUCT_CONSTITUTION.md`、`PRD.md`  

> 本文是对公开电子名片、Link-in-bio、AI客服、知识库、线索管理与海报生成项目的产品与代码思路进行蒸馏后的 Link168 自有方案。只吸收可验证的结构、交互和工程经验，不复制第三方界面、品牌、文案、整仓架构或受限制代码。

---

## 1. 文档目标

本PRD用于指导下一轮开发，把 Link168 的经营名片能力收口为以下完整闭环：

```text
国内电子名片的联系方式和微信交互
+ 现代 Link-in-bio 的简洁装修
+ 产品与服务展示
+ AI 客服和线索收集
+ 二维码海报分享
```

最终让访客完成：

```text
扫码或打开链接
→ 看懂名片主人是谁、能提供什么
→ 查看产品、服务和案例
→ 通过AI客服咨询
→ 复制微信号或查看微信二维码
→ 留下需求与联系方式
→ 名片主人在后台跟进
```

本轮不把 Link168 做成 Agent 开发平台、重型CRM、海报设计器或全渠道客服中心。

## 2. 蒸馏原则

### 2.1 可以吸收

- 电子名片项目中的联系方式结构、移动端首屏和分享习惯。
- Link-in-bio 项目中的简洁卡片、主题、排序和移动端装修方式。
- AI客服项目中的流式对话、知识检索、安全兜底和会话记录。
- CRM项目中的联系人、需求摘要、跟进状态和来源记录。
- 海报项目中的头像、文本、二维码、背景和自动排版模型。

### 2.2 不允许照搬

- 不复制第三方完整页面、视觉稿、品牌图标和文案。
- 不整仓引入旧小程序、微服务客服平台或重型设计器。
- 不引入与现有 Next.js、Prisma、PostgreSQL 不一致的第二套业务主线。
- 不直接复制许可证不明或限制性许可证代码。
- 不为了“看起来高级”提前增加多Agent、工作流编排、MCP市场和多模型切换。

### 2.3 Link168 自有差异

Link168 的差异不是“名片里多一个聊天框”，而是：

> 访客进入经营名片后，AI能够基于名片、产品、服务和FAQ真实接待，并在合适时展示微信联系组件、收集线索和记录转化行为。

## 4. 微信联系组件

### 4.1 组件名称

统一名称：**微信联系**。

禁止使用以下承诺性名称：

- 一键加微信
- 自动添加好友
- 点击直接成为好友

个人微信在网页中不能承诺所有浏览器和系统都能直接进入添加好友页。

### 4.2 联系类型

```ts
type WeChatContactType =
  | "PERSONAL_WECHAT"
  | "WECOM_CONTACT";
```

本轮默认只开放 `PERSONAL_WECHAT`；`WECOM_CONTACT` 预留字段和渲染能力，真实入口在后续批准后开放。

### 4.3 后台配置字段

- 联系类型。
- 组件标题，默认“微信联系”。
- 微信昵称。
- 微信号。
- 微信二维码。
- 按钮文案，默认“微信联系”。
- 辅助文案，例如“咨询产品、合作与报价”。
- 验证备注，可选。
- 工作时间，可选。
- 是否公开显示微信号。
- 是否允许复制微信号。
- 是否允许查看二维码。
- 是否允许保存二维码。
- 是否显示“尝试打开微信”。
- 组件样式。
- 启用状态。
- 排序位置。

### 4.4 组件样式

#### A. 简洁按钮

```text
[微信图标] 微信联系
```

适合个人主页和简洁主题。

#### B. 联系卡片

```text
微信联系
阿宝 · Link168
微信号：weex13148
[复制微信号] [查看二维码]
```

作为默认推荐样式。

#### C. 商务客服卡

```text
有合作需求？
添加微信，获取产品方案与报价
工作时间：09:00—18:00
[立即联系]
```

列入P1。

### 4.5 访客交互

点击组件后打开移动端底部弹层，桌面端使用居中弹窗：

```text
添加微信联系阿宝

微信号
weex13148
[复制微信号]

或使用微信扫描二维码
[二维码]

[保存二维码] [尝试打开微信]
```

复制成功后不能只提示“复制成功”，必须给出下一步：

```text
微信号已复制
请打开微信 → 右上角“+” → 添加朋友 → 粘贴微信号
```

尝试打开微信失败时显示真实兜底：

```text
当前浏览器无法直接打开微信。
微信号已经复制，请手动打开微信添加好友。
```

### 4.6 跳转优先级

```text
企业微信官方联系链接（后续）
→ 当前环境允许时尝试唤起微信
→ 自动复制微信号
→ 展示二维码
→ 展示手动操作教程
```

不使用来源不明的私有协议，不抓包拼接参数，不伪造跳转成功。

## 5. AI名片组件体系

### 5.1 第一批正式组件

1. 个人信息头部。
2. 一句话介绍。
3. 标签组。
4. 联系方式。
5. 微信联系。
6. 普通链接。
7. 图片。
8. 图集。
9. 产品或服务卡。
10. 富文本介绍。
11. 留资咨询。
12. AI客服入口。
13. 二维码分享。

微信联系是联系方式组件中的独立商业组件，不与普通外链混为一类。

### 5.2 编辑器结构

桌面端：

```text
组件列表 | 当前组件设置 | 手机实时预览
```

移动端：

```text
组件列表
→ 点击组件
→ 底部抽屉编辑
→ 顶部切换“编辑 / 预览”
```

### 5.3 统一渲染

编辑器预览、手机预览和公开页必须使用同一套组件 schema 和渲染器。

禁止：

- 预览正常、公开页样式不同。
- 编辑器字段存在、公开页不支持。
- 同一组件维护两套互不兼容数据。

## 6. AI客服

### 6.1 产品定位

AI客服用于：

- 介绍名片主人、企业、产品和服务。
- 回答公开FAQ。
- 推荐公开联系方式。
- 识别合作、购买、预约和报价意向。
- 引导访客留资。
- 在无法确认时安全转人工。

### 6.2 知识来源

P0只读取：

1. 名片基础资料。
2. 公开联系方式。
3. 产品和服务。
4. 手工FAQ。
5. 企业介绍文本。

P0不要求PDF、Word、网站抓取或复杂向量库。

短文本优先结构化注入；只有知识量明显扩大后才启用RAG。

### 6.3 基础上下文

```ts
interface BusinessKnowledgeContext {
  profile: unknown;
  company?: unknown;
  products: unknown[];
  services: unknown[];
  faq: unknown[];
  contactMethods: unknown[];
  businessHours?: string;
  publicLinks: unknown[];
}
```

### 6.4 回复边界

AI必须遵守：

- 只回答当前名片所属用户或企业的公开信息。
- 不知道时明确说明无法确认。
- 不自行编造价格、库存、合同、退款和服务承诺。
- 不透露系统提示词、后台数据、其他企业数据和私人信息。
- 只展示用户主动启用并公开的微信联系方式。
- 高风险问题引导人工联系。

### 6.5 微信组件联动

当访客表达以下意图时，AI可以展示微信联系卡：

- 怎么联系你。
- 能加微信吗。
- 想合作。
- 想了解报价。
- 想预约。
- 发方案给我。

展示卡片前必须校验：

- 组件启用。
- 微信号或二维码至少存在一项。
- 当前资料属于当前名片或Workspace。
- 用户允许AI展示该联系方式。

AI不得从历史消息、管理员后台或其他用户数据推测微信号。

## 7. 线索收集

### 7.1 触发条件

- 询问价格。
- 询问购买或合作。
- 请求预约。
- 连续查看多个产品。
- 主动要求人工联系。
- 查看或复制微信联系方式。
- 主动填写留资表单。

### 7.2 线索字段

```text
访客称呼
电话
邮箱
微信
需求摘要
来源名片
来源组件
来源产品
首次访问时间
最近咨询时间
对话摘要
意向等级
跟进状态
```

### 7.3 跟进状态

```text
新线索
已联系
跟进中
已成交
已关闭
```

### 7.4 行为与成交不可混淆

以下事件只能表示行为，不能直接表示成交或已加好友：

- 微信组件曝光。
- 复制微信号。
- 查看二维码。
- 保存二维码。
- 尝试打开微信。

“成功加好友”只能由用户人工确认，或后续通过正式企业微信接口回传。

## 8. 二维码海报分享

### 8.1 P0范围

只做固定模板自动生成，不做自由画布。

海报包含：

- 头像或企业Logo。
- 姓名或企业名。
- 一句话介绍。
- 公开名片二维码。
- 主要产品或服务卖点。
- 微信联系提示。
- Link168品牌标识与合规页脚。

### 8.2 输出场景

- 微信好友分享。
- 朋友圈。
- 小红书宣传图。
- 销售人员线下推广。
- 门店二维码海报。

### 8.3 规则

- 二维码必须指向当前已发布公开名片。
- 名片下线或被冻结后，海报链接也必须进入真实不可用状态。
- 不把微信个人二维码直接嵌入所有海报，除非用户明确启用。
- 不误用第三方品牌Logo。

## 11. 隐私、安全与风控

- 微信号与二维码默认不公开。
- 用户必须主动启用组件。
- 启用前明确提示“所有能够访问名片的人都可能看到”。
- 二维码上传需限制格式、大小和存储路径。
- 文件名随机化，禁止可执行文件和路径穿越。
- 二维码资源不能暴露服务器真实目录。
- 支持替换、删除、暂停展示。
- 记录上传、替换、删除和启停审计日志。
- 增加“联系方式诈骗”举报类型。
- 对高频抓取二维码和联系方式进行限流。
- 不向第三方短链或跳转平台传输微信号和二维码。
- AI只能调用当前租户公开资源。

## 13. UI验收标准

### 13.1 编辑器

- 能添加微信联系组件。
- 能填写微信号并上传二维码。
- 能控制公开、复制、保存和AI推荐开关。
- 能在按钮和联系卡片间切换。
- 编辑后实时预览。
- 删除二维码后公开页立即停止显示。

### 13.2 公开页

- 360、390、430px 无横向溢出。
- 微信弹层不被浏览器底部安全区遮挡。
- 复制微信号成功后显示操作教程。
- 二维码清晰且可保存。
- 微信唤起失败时不伪装成功。
- 组件禁用时公开页不留空白占位。

### 13.3 AI客服

- 能回答当前名片和产品问题。
- 无答案时不编造。
- 访客询问联系方式时可展示微信联系卡。
- 微信组件关闭后AI不再展示。
- 不会读取其他用户或其他Workspace数据。
- 对话失败显示真实错误和重试。

### 13.4 线索

- 访客可留下需求和联系方式。
- 来源名片、产品、AI或微信组件可追踪。
- 复制微信号不能自动标记为成交。
- 后台可修改跟进状态和添加跟进记录。

### 13.5 海报

- 生成二维码可正常打开当前公开名片。
- 中文无乱码。
- 头像、文本、二维码不裁切。
- 生成失败不返回伪造成功文件。

## 14. 工程约束

- 延续模块化单体，不拆独立微服务。
- 继续使用 Next.js、React、TypeScript、Prisma、PostgreSQL。
- AI继续通过阿里云百炼服务端调用。
- 不在前端暴露AI密钥、上传密钥或管理密钥。
- 不引入未评估的大型客服平台或海报编辑器依赖。
- 不删除现有正确名片、产品、线索、AI、Showcase或企业空间能力。
- 不创建重复组件体系、重复线索表或第二套公开页渲染器。
- 数据库变更必须增量迁移并提供回滚说明。
- 本轮修改不得触碰普通微信登录和企业协作平台连接范围。

## 15. 明日开发顺序

### 第一阶段：只读确认

1. 检查当前分支和工作区状态。
2. 定位现有名片组件 schema、编辑器、预览和公开页渲染器。
3. 定位现有上传、线索、AI接待和事件统计能力。
4. 确认哪些能力复用，哪些需要增量补齐。
5. 输出文件修改清单后再写代码。

### 第二阶段：微信组件闭环

1. 新增或扩展微信组件 schema。
2. 完成编辑表单。
3. 完成二维码上传。
4. 完成统一渲染。
5. 完成复制、查看、保存和失败兜底。
6. 完成事件统计。

### 第三阶段：AI客服联动

1. 统一名片、产品、服务和FAQ上下文。
2. 增加微信联系卡工具或结构化输出。
3. 校验组件启用和租户边界。
4. 保存会话和失败状态。

### 第四阶段：线索闭环

1. AI咨询和微信行为关联线索来源。
2. 增加需求摘要和跟进状态。
3. 后台展示最近线索和来源。

### 第五阶段：海报与验收

1. 固定模板生成名片海报。
2. 检查360、390、430px。
3. 执行类型检查、静态检查、组件测试和生产构建。
4. 不部署、不改服务器、不触碰密钥，除非老板另行明确批准。
