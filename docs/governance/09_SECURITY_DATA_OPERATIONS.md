# Link168 V2 安全、数据与运行治理

**文件名：** `docs/governance/09_SECURITY_DATA_OPERATIONS.md`  
**版本：** v1.0  
**生效日期：** 2026-07-12  
**性质：** 安全、数据、发布与生产运行治理附件  
**上位规则：** `PRODUCT_CONSTITUTION.md` v1.6、`PRD.md` v2.0-rc8、`PROJECT_RULES.md` v1.0-rc3

> 本文件集中补齐安全、数据保留、事件响应、API兼容、数据库迁移、依赖管理、监控告警和发布检查，避免建立多份互相重复的治理文档。具体产品期限、价格、权限和用户承诺仍以宪法、PRD及正式配置为准。

## 1. 责任边界

- **Agent01 项目总控：** 组织重大风险裁决、事故升级和跨模块恢复。
- **Agent03 架构与数据：** 数据模型、迁移、加密边界、API兼容和恢复设计。
- **Agent04 后端：** 服务端鉴权、输入校验、幂等、第三方验签和错误处理。
- **Agent06 AI：** AI密钥、知识库隔离、额度账本、提示注入与高风险输出控制。
- **Agent07 QA与安全：** 安全检查、权限回归、事故复盘验证和发布验收。
- **Agent08 DevOps：** 部署、备份、监控、告警、密钥环境和运行恢复。
- **老板/明确授权负责人：** 产品规则、生产高风险操作、破坏性变更和最终事故决策。

Agent是职责角色，不等于平台管理员、超级管理员或GitHub账号。

## 2. 安全开发基线

所有正式能力必须满足：

1. 服务端鉴权和资源归属校验。
2. 企业数据同时校验`workspaceId`、角色和资源范围。
3. 输入进行类型、长度、格式、枚举和业务约束校验。
4. 输出不暴露堆栈、SQL、内部路径、Token、密钥和第三方敏感标识。
5. 支付、身份回调、AI扣点、卡密和佣金使用幂等控制。
6. 高风险操作记录操作者、时间、原因、对象和变更前后状态。
7. 文件上传校验大小、类型、扩展名、归属和可访问范围。
8. 不以隐藏按钮代替服务端权限控制。
9. 不使用假支付、假邮件、假AI或假第三方成功状态。
10. 未配置的外部服务必须明确失败、隐藏或降级。

## 3. 数据分级

| 级别 | 示例 | 基本要求 |
|---|---|---|
| 公开数据 | 已发布经营名片、公开产品信息 | 只展示用户明确发布内容，支持下线和纠错 |
| 内部数据 | 普通运营配置、非敏感聚合统计 | 登录后按职责访问，不进入公开页面 |
| 敏感数据 | 邮箱、手机号、客户线索、订单、企业资料、AI使用记录 | 最小化采集、按角色访问、传输加密、日志脱敏 |
| 高敏数据 | 密码哈希、支付私钥、数据库密码、会话密钥、AI密钥、原始Token | 不进入前端、仓库、报告或明文日志；仅受控服务端环境访问 |

不得因为调试方便降低数据等级。

## 4. 数据保留与删除

### 4.1 原则

- 只保留完成业务、履行合同、安全审计和合规所必需的数据。
- 具体期限由PRD、用户协议、隐私政策、合同、法律要求和正式服务端配置共同确定。
- 未在正式文件中批准的期限不得由Agent自行写死为永久保存。
- 原始IP、设备标识和安全明细采用短周期受控保存；如当前正式规则已经规定90天，继续按该规则执行，调整必须同步PRD和隐私说明。
- 聚合且不可反向识别个人的数据可以按经营分析需要延长保存。

### 4.2 删除与注销

- 用户注销不得删除仍属于企业空间的客户、企业名片和工作记录。
- 订单、退款、发票、安全和审计数据按必要期限保留后再删除或匿名化。
- 删除操作必须可追踪，批量删除和不可逆清理需老板明确批准。
- 备份中的数据按照备份周期自然过期，不承诺即时从所有离线备份物理擦除，除非正式规则另有要求。

### 4.3 测试数据

- 测试环境不得复制无脱敏的生产客户、支付和身份数据。
- 演示数据必须明确属于测试环境，不能在正式用户页面冒充真实业务结果。

## 5. 密钥与凭证

- 密钥只存放在服务器环境变量或批准的受控配置中心。
- `.env`、私钥、证书、Token和数据库连接串不得提交GitHub。
- 日志只记录配置是否存在，不打印配置值。
- 权限按最小必要原则分配；开发Agent默认不能读取生产密钥。
- 密钥泄露、人员离开、供应商异常或怀疑被滥用时必须轮换。
- 轮换后验证旧凭证失效、服务恢复和审计记录完整。

## 6. API兼容策略

### 6.1 默认规则

- 内部和公开API默认保持向后兼容。
- 新字段优先采用可选字段，不改变旧字段含义。
- 不在同一路径中无提示改变状态码、金额单位、枚举含义和权限语义。
- 页面和API不得各自维护不同的套餐、角色和状态真相。

### 6.2 破坏性变更

破坏性变更必须同时具备：

1. 影响清单。
2. 老板或明确授权负责人批准。
3. 新旧版本兼容期或迁移适配层。
4. 数据迁移和调用方迁移方案。
5. 回滚或补偿方案。
6. PRD、代码地图、ADR和发布说明同步更新。

不得为了目录整洁直接删除仍被公开链接、支付回调或历史客户端使用的接口。

## 7. 数据库迁移策略

- 数据库事实来源为`prisma/schema.prisma`和正式migration。
- 生产只执行`prisma migrate deploy`，禁止`prisma migrate reset`。
- 迁移必须评估历史数据、空值、默认值、索引、锁表时间、数据量和兼容窗口。
- 高风险字段变更采用“新增字段 → 双读/双写或回填 → 切换 → 后续版本清理”的渐进方式。
- 删除表、字段、枚举值和历史模型前必须完成依赖、生产数据和回滚评估并取得老板批准。
- 数据迁移脚本需要可重复执行或具备幂等保护，并记录执行结果。
- 数据库回滚优先采用向前修复migration；不能假设所有DDL都可安全反向回滚。

## 8. 依赖管理

新增或升级依赖必须说明：

- 实际用途和无法使用现有依赖解决的原因
- 许可证
- 维护活跃度
- 已知安全风险
- 包体和运行成本
- Node、Next.js、React和Prisma兼容性
- 回退方式

规则：

- 禁止无理由使用`latest`新增正式依赖。
- 现有`latest`依赖应在专项升级任务中逐步固定，不在普通功能任务中顺手全量升级。
- 锁文件变化必须审查，禁止夹带无关大规模版本漂移。
- 安全扫描结果需要人工判断可利用性和业务影响，不能为追求“0告警”盲目升级并破坏生产。
- 高危且可利用的问题阻止发布；无法立即修复时必须记录临时缓解、责任人和复查条件。

## 9. 监控与告警

最低监控范围：

- 网站可用性和核心健康接口
- PM2进程、CPU、内存、磁盘和端口
- PostgreSQL连接、容量、慢查询和备份状态
- 注册、登录、邮件、支付回调和退款失败率
- AI调用成功率、延迟、成本、扣点与回补异常
- 企业身份回调和组织同步失败
- 5xx、未捕获异常和定时任务失败

告警必须包含：

- 发生时间
- 环境和服务
- 影响范围
- 关联请求或任务标识（不得包含密钥）
- 初步错误类别
- 建议检查入口

当前阶段不强制引入Prometheus、Grafana或复杂平台；优先使用现有云监控、PM2、应用日志和数据库能力。只有真实需要时再升级工具。

## 10. 事件响应

### 10.1 事件级别

| 级别 | 判定示例 | 处理要求 |
|---|---|---|
| SEV-1 | 数据泄露、跨企业访问、支付错账、大面积不可用、密钥泄露 | 立即停止扩大影响，老板/总控介入，优先隔离和恢复 |
| SEV-2 | 核心功能明显失败、部分用户无法登录或支付、AI账本异常 | 尽快降级或修复，记录影响和补偿 |
| SEV-3 | 非核心功能异常、局部性能或展示问题 | 纳入正常修复流程 |

SEV级别只用于生产事件，不等同于产品P0/P1/P2优先级。

### 10.2 标准流程

```text
发现
→ 确认影响与级别
→ 停止扩大影响
→ 隔离、降级或回滚
→ 恢复核心服务
→ 核对订单、会员、AI额度和企业数据
→ 通知受影响人员
→ 形成复盘与防复发任务
```

事故处理中不得为了快速恢复而清空生产数据、绕过租户隔离或关闭关键审计。

### 10.3 复盘内容

- 时间线
- 用户和数据影响
- 根因
- 为什么现有检查未发现
- 临时处置
- 永久修复
- 补偿和沟通
- 责任Agent和验证证据

复盘用于改进系统，不用于隐藏问题或伪造已恢复状态。

## 11. 发布检查清单

发布前至少确认：

```text
[ ] 部署源为 codex/link168-v2-direction 的明确commit或批准Tag
[ ] diff仅包含本次范围
[ ] npm run governance:check通过
[ ] 相关lint、typecheck、测试和build通过
[ ] 数据库migration已审查且目标数据库正确
[ ] 未提交密钥、上传文件、构建缓存和无关文档
[ ] 支付、身份、AI、企业和权限变更有专项验证
[ ] 旧路径、公开链接和API兼容已检查
[ ] 备份、回滚或补偿方式明确
[ ] 部署后健康检查和核心路径清单明确
```

真实第三方未验证时必须标记“未验证”，不得写成生产通过。

---

## 12. 紧急修复

- 紧急修复可以缩短流程，但不能跳过范围确认、密钥保护、数据备份、最小验证和事后复盘。
- 涉及数据库、支付、会员、AI额度、企业隔离和身份的紧急修复必须由对应Agent与总控共同复核。
- 紧急修复不得永久绕过正常鉴权、审计和幂等；临时措施必须有撤销任务。

---

## 13. 治理更新

以下变化必须同步本文件：

- 新增高敏数据类型
- 数据保留或删除承诺改变
- API版本与弃用策略改变
- 数据库迁移方式改变
- 监控、备份或事故响应责任改变
- 新增重要第三方服务

每次正式版本冻结、解冻、重大架构变更或生产事故复盘后，由Agent01组织、Agent03/07/08参与复核；规则改变仍需遵守产品宪法规定的批准权限。
