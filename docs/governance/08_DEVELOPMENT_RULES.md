# Link168 V2 日常开发执行规则

**文件名：** `docs/governance/08_DEVELOPMENT_RULES.md`  
**版本：** v1.1  
**生效日期：** 2026-07-12  
**性质：** 工程执行检查表  
**上位规则：** `PRODUCT_CONSTITUTION.md` v1.6、`PRD.md` v2.0-rc8、`PROJECT_RULES.md` v1.0-rc3

> 本文件把工程规则转换为Agent可以直接执行的日常流程。发生冲突时，正式根目录文件优先。

至少确认：

```text
当前仓库
当前分支
当前HEAD
工作区状态
当前diff
目标文件是否有其他Agent改动
正式文档版本
任务所属模块
允许和禁止范围
数据库是否允许修改
是否允许新增依赖
是否允许真实第三方调用
是否需要部署
```

正式目标：

```text
weex13148-gif/link168.me
codex/link168-v2-direction
```

旧master、旧工作区和归档副本不作为V2正式事实。

## 4. 修改优先级

1. 修复服务端权威规则。
2. 修复领域服务和数据一致性。
3. 修复API鉴权、错误和状态。
4. 修复页面交互和显示。
5. 修复样式、空状态和细节。

禁止只在前端隐藏问题而保留可绕过的服务端漏洞。

---

## 5. 保留与删除

默认：

> 保留优先、功能开关限制、删除需老板批准。

未完成能力优先采用：隐藏入口、服务端拒绝、禁用、降级、只读或兼容跳转。

删除页面、路由、字段、模型、migration、支付、会员、AI、企业、卡密、推广、知识库、身份连接或未来结构前，必须给出：

- 删除清单
- 原因和依赖
- 数据与生产影响
- 迁移与兼容方案
- 回滚或补偿方案
- 老板批准记录

---

## 6. 前端规则

- 用户后台一级分类只能是：首页、名片、客户、AI、我的。
- 新功能进入现有分类的组件或二级页面。
- 用户侧新页面进入`/console`，平台管理进入`/jeepwork`。
- 普通用户和企业管理员不得看到Jeepwork导航入口。
- 优先保证360–430px，再适配桌面。
- 编辑器、手机预览和公开页尽量使用统一渲染。
- 数据加载失败不得伪装成0。
- 重要页面必须有加载、空、错误、权限和成功状态。
- 页面不得显示开发中、待接入、Demo、Mock、Agent报告或技术债。

---

## 7. 服务端规则

- 所有关键权限在服务端校验。
- 不信任前端传入的角色、套餐、金额、AI额度、Workspace或支付结果。
- 写入校验资源归属，企业查询校验`workspaceId`、角色和资源范围。
- 重要写入使用事务、幂等或补偿。
- API返回稳定错误代码和可理解信息，不暴露堆栈、SQL和敏感标识。
- 日志不记录密钥、密码、完整Token或不必要敏感正文。

---

## 8. 身份、会员、支付、AI和企业规则

### 身份

- 内部User ID是唯一主账号标识。
- 外部身份冲突时停止，不覆盖、不自动合并。
- 微信注册可靠完成User、个人空间、绑定和Session。
- 待激活企业成员没有企业数据访问权。

### 会员与支付

- 正式套餐只有免费版、Plus、Pro、企业版、企业Pro。
- 价格和权益来自唯一服务端配置。
- 支付宝回调校验签名、订单、金额、状态和幂等。
- 退款同步处理会员、AI、卡密、佣金、企业权益和发票。

### AI

- 免费用户不能购买AI加量包或调用六大AI Agent。
- 套餐、购买和企业额度分账。
- 扣点保存来源和批次；失败回补原来源和原批次。
- 企业知识库不得跨Workspace检索。

### 企业

- 企业管理员只管理本企业。
- 通讯录同步只创建待激活成员。
- 离职冻结企业访问，保留个人账号和企业资产。
- 企业协作平台差异封装在连接器适配层。

---

## 9. API兼容规则

- API默认向后兼容。
- 新字段优先可选，不无提示改变旧字段含义。
- 金额单位、枚举、状态码、权限语义和回调路径不能静默改变。
- 破坏性变更必须有批准、调用方清单、兼容期、迁移、回滚和文档更新。
- 公开链接、支付回调和企业连接器不得因目录清理直接删除。

详细规则见`09_SECURITY_DATA_OPERATIONS.md`和ADR-015。

---

## 10. 数据库规则

- 数据库事实以`prisma/schema.prisma`和migration为准。
- 生产只允许`prisma migrate deploy`，禁止`prisma migrate reset`。
- 禁止手工改生产表代替migration。
- 新migration评估历史数据、空值、默认值、索引、锁表和兼容窗口。
- 高风险变更采用新增、回填、切换、观察、后续清理的渐进方式。
- 删除模型和字段必须专项评估并取得老板批准。
- 数据迁移脚本具备幂等或重复执行保护。

---

## 11. 第三方服务规则

适用于邮件、支付宝、AI、微信、企业协作、存储和域名：

- 服务端调用
- 配置存在性检查
- 验签或凭证校验
- 幂等
- 超时
- 重试或补偿
- 错误记录
- 降级
- 不输出密钥
- 不伪造成功

第三方未配置时返回真实不可用状态或隐藏入口。

---

## 12. 密钥与安全规则

严禁提交：

- `.env`、`.env.local`、`.env.production`
- 数据库密码、Session密钥、配置加密密钥
- 邮件凭据、支付私钥、AI密钥
- OSS密钥、Token、密码和私有证书

安全要求：

- 最小权限
- 输入校验
- 文件上传校验
- 高风险操作审计
- 企业租户隔离
- 日志脱敏
- 依赖风险审查

详细分级、事故和发布要求见`09_SECURITY_DATA_OPERATIONS.md`。

---

## 13. 依赖规则

- 没有明确需要不新增依赖。
- 新依赖说明用途、许可证、维护状态、安全、体积、兼容和回退方式。
- 不使用不受控的`latest`新增正式依赖。
- 现有`latest`在专项任务中逐步固定，不在普通功能任务中全量升级。
- 锁文件变化必须审查，不夹带无关升级。
- 安全扫描结果需要人工判断可利用性；高危且可利用的问题阻止发布。

不设置脱离现有测试基础的固定“80%覆盖率”口号。测试门槛按风险、改动和关键路径确定，并逐步建立可度量基线。

## 14. GitHub PR与审批流程

### 14.1 PR模板

使用`.github/pull_request_template.md`填写：

- 主负责Agent和主模块
- 允许与实际修改范围
- 是否跨模块
- 数据库、API、依赖、第三方和安全影响
- 实际验证命令
- 发布、回滚和未验证事项

### 14.2 审批

- `.github/CODEOWNERS`绑定真实GitHub账号，不使用虚假Agent账号。
- 跨模块变更由Agent01协调、Agent03审查接口、Agent07验证。
- 产品、冻结和破坏性变更仍需老板批准。
- 数据库、支付、身份、AI账本和企业隔离按`05_AGENT_GOVERNANCE.md`审批矩阵执行。

### 14.3 合并前

- 治理检查通过
- 相关质量检查通过
- 无未解释的无关diff
- 无密钥和生产数据
- 风险、迁移和回滚明确

## 15. 自动化治理与CI

本仓库提供：

```text
npm run governance:check
```

它检查：

- 根目录正式文件和治理附件是否完整
- 治理附件是否引用当前宪法、PRD和工程规则版本
- README与DOCUMENT_INDEX是否登记全部治理附件
- 治理文件编号是否重复
- 根目录是否出现并行宪法或并行PRD

GitHub Actions执行同一脚本。

自动化不得采用简单关键词黑名单阻止CRM、Dashboard、Workbench等词，因为兼容代码、历史迁移和正式说明仍可能合法包含这些术语。

## 16. 测试与检查

### 单模块修改

- `npm run governance:check`
- 相关类型检查
- 相关lint或静态检查
- 相关单元、组件或API测试
- 必要的手工路径验证

### 阶段收口

- `npm run governance:check`
- `npm run typecheck`
- 关键业务测试
- 权限、Workspace和数据差异检查

### 最终验收或上线前

- `npm run governance:check`
- `npm run lint`
- `npm run typecheck`
- 生产build
- 注册、登录、名片、留资、客户、会员、支付、AI和Jeepwork核心验收
- 360–430px移动端验收
- 密钥、临时文件和构建缓存检查

不得为每个小改动重复全量构建，也不得为全绿删除业务功能。

---

## 17. 真实验收边界

| 表述 | 含义 |
|---|---|
| 代码存在 | 找到实现，不代表可用 |
| 静态检查通过 | 类型或lint通过，不代表运行通过 |
| 本地Mock通过 | 仅模拟流程通过 |
| 沙箱通过 | 第三方沙箱验证通过 |
| 真实环境通过 | 有真实订单、回调、调用或日志证据 |
| 生产通过 | 正式环境验证且未破坏真实数据 |

禁止把前四种表述写成“生产已通过”。

## 18. Git规则

未经老板明确授权不得：

- force push
- 改写历史
- 删除正式分支或Tag
- 合并独立历史
- 修改分支保护
- 创建大量临时分支
- 自动推送或发起PR

获得授权后：

1. 只读确认仓库、分支、HEAD、remote、status和diff。
2. 只暂存本任务文件。
3. 使用清晰提交信息。
4. 不混入无关格式化、临时文件和其他Agent改动。
5. 推送后检查远端文件和分支。

---

## 19. 发布与部署规则

### 第一步：只读确认

不得上传、覆盖、重启、改配置或改数据库，只确认：服务器目录、部署源、待上传和排除清单、PM2、端口、Nginx、数据库目标、migration、环境变量名称、构建产物和磁盘空间。

### 第二步：老板批准后执行

- 覆盖正式程序文件
- 安装正式依赖
- 执行批准migration
- 构建
- 重启PM2
- 验证本机和公网核心路径

部署不得上传正式运行不需要的Markdown、PRD、审计、报告和比赛资料。

发布清单、监控和事件处理见`09_SECURITY_DATA_OPERATIONS.md`。

---

## 20. 紧急修复

- 可以缩短流程，但不能跳过范围确认、密钥保护、备份、最小验证和事后复盘。
- 支付、身份、AI额度、企业隔离和数据库问题必须由对应Agent与Agent01/07复核。
- 临时绕过必须有撤销任务，不能永久关闭鉴权、审计或幂等。
- 紧急修复不能借机扩大产品范围。

---

## 21. 并发规则

- 同一文件同一时刻只有一个写入Agent。
- Agent01维护文件锁。
- 共享文件由唯一负责人修改。
- 其他Agent通过交接提出要求，不直接并写。
- 应用补丁前读取最新文件和diff。
- 不使用全局格式化制造大面积无关变化。
